# 17 · 并发与容量

> 这一篇是"高并发能不能扛住"的一次完整排查与加固的记录：**哪里会先垮、为什么、改了什么、量出来是多少、
> 旋钮在哪、还有什么没做。** 每个数字都能用 `deploy/scripts/loadtest/` 里的脚本复现；
> 每一次改动的完整推理在对应提交的说明里（`git log --oneline` 找 `fix(order)`、`perf(...)`、`feat(agent)`）。

## 先说结论

这个项目有两类负载，瓶颈完全不同：

| | 瓶颈 | 为什么 |
|---|---|---|
| **下单（mall-product）** | MySQL 行锁 + Hikari 连接池 | 热点 SKU 的请求在同一行库存上排队，每个排队的请求占着一条连接（池 10 条） |
| **对话（ai-agent）** | LLM 调用 | 一轮对话是几秒的等待，线程大部分时间在睡觉；机器几乎是闲的，**要保护的是"别让排队无限长"** |

下面按"请求从进来到落库"的顺序，每一层一张表。

## 1 · 下单

| 问题 | 改动 | 实测（真 MySQL 8） |
|---|---|---|
| 订单号用随机后缀，生日悖论：1000 TPS 时每秒约 0.05% 撞号，撞了返回 500 | `OrderNoGenerator`：时间戳 + 节点号 + 序号，同节点同秒 <10⁴ 笔按构造不重号；撞号时整笔重试 | 压测 200 TPS 实测撞出一次；改后按构造不撞 |
| 超时回收一次只扫一批，积压了翻不完；一个"毒单"（回收时抛异常）会永远挡在队头 | 一次触发翻完积压；每单独立 try/catch；查询改按 `(created_at, id)` 游标走 `idx_status_created` | 查询 310ms → 4ms（30 万行）；一次触发 26 批、约 20 秒收完 5000 笔，库存精确回补 |
| 热点 SKU 的请求占满连接池，**别的商品**也下不了单 | 语句顺序改成"先插单、后条件扣库存"（行锁只在最后持有）；`PlacementGate`：每 SKU 最多 4 个并发、全局 64，等 200ms 拿不到就快速失败 | DB 层热点 TPS 444–469 → 705–709；热点洪水（300 并发）期间旁观请求 p50 **1737ms → 16ms**；分散负载无回退 |

**诚实的局限**：热点 SKU **自身**的 p99 没有改善（4.6s → ~6s）。闸门保护的是"别的商品"，不是热点本身。
要让热点本身扛住秒杀，需要 Redis 预扣库存 + 异步落库——**这个刻意没做**，见文末"需要你拍板的"。

## 2 · 商品列表与对话链路

| 问题 | 改动 | 实测 |
|---|---|---|
| `/api/products` 每个请求都 `from_env()` 建一个连接池，且在 `async def` 里同步查库，整个进程的请求（含 `/health`）排队 | 进程内按 DSN 共用连接池；查询放线程池；TTL 缓存 + 单飞 + ETag/gzip/304；下单成功后立即作废缓存 | 并发 30 的 p99 14116ms → 346ms；`/health` 最大等待 13362ms → 141ms；490KB → 44KB |
| 对话 REST 接口同步跑整轮；ai-rag 的 `/search` 同步阻塞 | 整轮放进专用线程池（64 线程，不用 asyncio 默认的 8 个）；同一会话串行；ai-rag 放线程池 | 20 并发：总耗时 3.04s → 0.19s，事件循环最大延迟 3019ms → 5ms |
| 对话检索实际走的是进程内暴力检索，compose 里的 Milvus 虽然起着却不在查询链路上；Milvus 索引写入后不 `flush`，检索慢 6 倍 | `RETRIEVER_BACKEND=http` 走 ai-rag + Milvus；索引后 `flush`；查询向量 LRU 缓存 | 单次检索（Milvus Lite）5000 条：本地 226ms，Milvus 未 flush 1468ms → flush 后 53ms；20000 条：本地 919ms 对 55ms。压测 20 线程只有 29 次/s，Lite 是嵌入式的，扛不住并发；服务端 Milvus 没压过 |

## 3 · 对话入口的过载保护（`app/overload.py`、`app/ratelimit.py`）

线程池的任务队列是**无界**的。洪峰进来 400 个请求、每轮 2 秒、客户端 6 秒超时：64 个拿到答案，
其余 336 个客户端早已放弃，**服务端却把它们一个个跑完**——白花 LLM 的钱，还把后来的人往后挤。

一个请求要依次过四道关（**顺序是有讲究的**，见 `overload.py` 顶部的说明）：

1. **限流**（令牌桶，按 IP 与按用户/会话两道）——在创建会话之前，被限流的请求不往会话表里塞对象
2. **会话待处理上限**（同一会话最多 2 条在途）
3. **会话锁**（同一会话串行）——在全局名额之前，否则一个用户排队的消息占着名额干等锁
4. **全局名额**（= 工作线程数）——超出的进有上限、有超时的等待区，满了立刻拒；名额在**线程结束时**归还，不是协程退出时

被拒绝时：REST 返回 503/429 + `Retry-After`；WebSocket 发 `{"type":"error","code":"busy"|"rate_limited"|"session_busy"}`
（前端对 `error` 的现有处理正好把 `answer` 显示成气泡，前端零改动，有测试读前端源码守住这个契约）。

| 场景（真 uvicorn，LLM 桩成固定耗时） | 旧 | 新 |
|---|---|---|
| **洪峰**：400 请求 / 32 线程 / 2s 一轮 / 客户端超时 6s | 64 成功，336 超时；服务端跑了 401 次 LLM（**336 次白跑**）；洪峰之后才来的用户等 **21.2s**；服务端 28.7s 后才空闲；洪峰中途单发的 20 个请求全部 15s 超时 | 64 成功，336 被快速拒绝；LLM 调用 64 次（**0 次白跑**）；后来的用户 **2.0s**；服务端 9.0s 空闲；中途请求 14 个 3–4ms 被拒、6 个排上队 3.7s 完成 |
| **滥用**：1 个不停换 session_id 的滥用者 + 8 个正常用户（限流计数放真 Redis） | 正常用户 17 次请求只有 6 次成功（p50 9.8s），11 次超时 | 滥用者 2403 次被 429、仅 49 次放行；正常用户 33 次请求 32 次成功（p50 1.0s） |

两个版本的 `/health` 都不受影响——事件循环本来就没被占住；这次改动的收益在"有效产出"和"洪峰后的恢复"。

**会话存储**（`app/sessions.py`）：内存版 `get()` 原来每次遍历全部会话（5 万个时 1.57ms，在事件循环里），
现在摊销 O(1)（0.0007ms），并有 `SESSION_MAX` 上限。可选 Redis 持久层（`SESSION_BACKEND=redis`）：
重启/发版后接着聊、WebSocket 重连落到别的实例上下文不断、导购累积的需求不丢；同一会话的一轮对话
跨实例用分布式锁串行；每轮多花约 1ms；Redis 故障时自动退回纯内存。

## 4 · 数据库

### 4.1 agent_trace 的实测（MySQL 8，100 万行 ≈ 1GB）

- **写入不是问题**：16 线程单行自动提交 ≈ 2500 条/秒，从 1.3 万行到 100 万行没有退化；
  对话入口本来就只有几十轮/秒。
- **读才是问题**：`product_demand`（"用户对这件商品问得最多的是什么"）耗时随历史行数线性涨
  （0.8ms @1 万行 → 12ms @100 万行，线性外推到一年是秒级）。它是分析查询，没理由扫三年前的对话。
- **buffer pool 伤的是读**：`O_DIRECT`（让 buffer pool 成为唯一的缓存）下，128MB → 1GB 使
  `product_demand` p50 **103ms → 6.2ms**（复测 128MB 为 93ms），写入只涨约 10%。
  默认 `O_DIRECT` 关着时 OS page cache 会兜底，这个差别被遮住了。
- **redo 日志大小不是瓶颈**：从 100MB 提到 1GB 没有更快（`Innodb_log_waits` 始终 0），所以**不建议改**。

### 4.2 改了什么

| | |
|---|---|
| `docker-compose.base.yml` | `--innodb-buffer-pool-size`（默认 1G，`MYSQL_BUFFER_POOL_SIZE`）、慢查询日志默认开（0.5s）。**刻意没动** `innodb_flush_method`（个别文件系统不支持 `O_DIRECT`，MySQL 会起不来）和 redo 大小（没有证据） |
| 本机 MySQL | `doctor.py` 新增体检：数据+索引逼近 buffer pool 时提醒并给出 `SET PERSIST innodb_buffer_pool_size = ...`（8.0 在线生效、重启保留，不用改 my.ini）；连接预算；慢查询日志。每条规则的两边都有单测（`deploy/tests/test_dbtune.py`） |
| `agent_trace` 归档 | 迁移 015 + `python -m smartmall_pipeline.cli archive-traces`：把超过保留期（默认 90 天）的行**搬**到 `agent_trace_archive`（不是删）。分批（每批一个事务）、可中断可重跑、带点赞点踩的行默认留在在线表（它们是训练数据）、遇到死锁只重做这一批 |
| `product_demand` | 默认只统计最近 90 天（与归档保留期对齐）；传 `since_days=None` 恢复全部历史。**这是语义变化**：三个月前的问题不再计入"用户最关心什么" |
| 点赞迟到 | 在线表 UPDATE 不到时回头更新归档表；遇到死锁/锁等待重试。点赞是最值钱的字段，不能因为归档就丢 |

### 4.3 归档运行手册

```bash
python -m smartmall_pipeline.cli archive-traces --dry-run          # 先看会搬多少、有多少带点赞的会留下
python -m smartmall_pipeline.cli archive-traces                    # 默认保留 90 天
python -m smartmall_pipeline.cli archive-traces --max-seconds 600  # 放进维护窗口，到点干净地停，下次接着搬
```

- 放进 cron / Windows 任务计划程序每天跑一次。需要先 `make db-init` 应用 015 迁移。
- 删除行**不会**缩小 InnoDB 文件（空页留给后续插入复用）。要把磁盘还给系统，维护窗口里 `OPTIMIZE TABLE agent_trace`（会重建表、短暂阻塞写入，不自动做）。
- **归档刚结束时实例还在刷脏页，延迟会比较难看**（实测见下）；稳态后恢复。放在低峰跑，别在它刚结束时拿查询耗时下结论。

**归档的真 MySQL 验证**（`deploy/scripts/loadtest/db_trace_bench.py`；100 万行；线上写入与点赞同时进行）：

| | 128MB buffer pool，线上写入不限速（16 线程，压力上限） |
|---|---|
| 归档 | 730,032 行 / 381 批 / 782s（约 930 行/秒） |
| 正确性 | 在线 281,158 + 归档 730,032 = 原 1,011,190；两表重复 0；内容校验和一致 |
| 期间的点赞 | 25,675 次，**一条没丢**（其中 9,593 次落在已归档的行上，靠回退到归档表） |
| 对线上写入的影响 | 插入 2517/s → 1387/s，p99 14.9 → 34.7ms，max 569ms |
| 归档刚结束时 | 实例还在刷 1.7 万个脏页，`product_demand` 一度 1128ms；刷完回到 7–8ms（`history_len`=0，执行计划没变——不是回退） |

这一轮是**压力上限**：不限速的 16 个写入线程把归档期间灌进了 110 万行，而这个项目设计的对话峰值只有几十轮/秒。


### 4.4 连接预算

没有"最优值"，只有算术：每个服务的连接池上限相加不能逼近 `max_connections`（compose 里 300）。
按每个服务 1 个副本：4 个 Java 服务各 10 = 40；每个 Python 进程 `MYSQL_POOL_SIZE + MYSQL_MAX_OVERFLOW` = 20。
**扩副本要乘上去。** `doctor.py` 会按实际配置算出最坏需要多少条，并对照历史峰值 `Max_used_connections`。

对话的 64 个工作线程远大于连接数（20）并不是问题：一轮对话只在写埋点、查订单这类毫秒级 SQL 上占着连接
（单行 INSERT p50 5ms），线程大部分时间在等 LLM。20 条连接撑得住每秒上千轮。

## 旋钮清单

| 变量 | 默认 | 说明 |
|---|---|---|
| `CHAT_WORKERS` | 64 | 同时在跑的对话数 = 线程数 |
| `CHAT_MAX_WAITING` / `CHAT_QUEUE_TIMEOUT` | 64 / 8s | 等待区长度与最长等待；满了或超时就拒 |
| `CHAT_SESSION_MAX_PENDING` | 2 | 同一会话最多几条在途 |
| `CHAT_RATE_BACKEND` | memory | `memory` / `redis` / `off`；redis 在多实例下共用额度，故障时退回 memory |
| `CHAT_RATE_IP_BURST` / `_PER_MIN` | 30 / 60 | 每 IP 突发与长期速率（宽松：一个出口 IP 后面可能是整个办公室） |
| `CHAT_RATE_IDENTITY_BURST` / `_PER_MIN` | 6 / 12 | 每用户（无 user_id 则按会话） |
| `CHAT_TRUST_PROXY_HOPS` | 0 | 前面几层可信代理。**站在代理后面必须设**，否则所有用户共用一个 IP 桶；别设得比实际层数大 |
| `SESSION_BACKEND` | memory | `redis` 开持久层；compose 已设 |
| `SESSION_MAX` / `SESSION_TTL` | 50000 / 24h | 进程内最多缓存多少会话（LRU，正在跑的不淘汰） |
| `SESSION_LOCK_TTL` / `SESSION_LOCK_WAIT` | 120s / 3s | 分布式锁过期（必须大于一轮对话的最长耗时）与最长等待 |
| `MYSQL_POOL_SIZE` / `MYSQL_MAX_OVERFLOW` | 10 / 10 | Python 进程的连接池 |
| `MYSQL_BUFFER_POOL_SIZE` | 1G | compose 里的 mysql；本机 MySQL 见 `doctor.py` 的提示 |
| `smartmall.order.gate.*` | 4 / 64 / 200ms | 下单闸门：每 SKU 并发、全局并发、最长等待。**全局上限别设得比 Hikari 池小**（设成 8 时分散流量被误拒 22%） |

## 没做的，以及需要你拍板的

**需要你拍板：Redis 热点库存预扣（Lua 原子扣减 + 异步落库）。** 这是让热点 SKU 本身扛住秒杀的标准做法，
但它引入了真实的一致性风险：Redis 与 MySQL 的库存是两份数据，Redis 扣了、落库失败（或进程在两者之间崩了），
就会"超卖/少卖"；要安全地做，需要预扣流水 + 对账任务 + 超时回补，而且**库存的权威来源要想清楚是谁**。
这不是顺手能加的东西，也没法在没有你的业务取舍的情况下替你定。如果你的业务确实有秒杀场景，说一声，
我按"Redis 只做准入、MySQL 仍是权威、对账兜底"的保守方案来做。

**已知局限（都写在对应代码的 docstring 里）：**

- 会话分布式锁没有续期：一轮超过 `SESSION_LOCK_TTL` 锁会过期，另一个实例可能插进来（释放时会告警，写回后写者胜）。
- 会话写回是整份 JSON；历史无限增长时开销会涨，该做摘要截断。
- 用户身份（`user_id`）是客户端自报、未认证的，按用户的限流桶防不了有意绕过——那是 IP 桶的活。
- Milvus 服务端（非 Lite）的并发上限没有压测过。
- `LocalRetriever` 的稠密检索仍是纯 Python（5000 条约 250ms），现在只是开发路径。
- 没有做 `/api/products` 的服务端分页：缓存 + gzip + 304 之后全量列表单次约 1ms CPU，分页要重做前端交互，收益不抵成本。
