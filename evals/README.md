# evals —— 评测集与评测脚本

13 个评测集，与代码同仓版本管理。详见 [docs/12-eval-observability.md](../docs/12-eval-observability.md)。

## 硬性约束

**评测集样本绝不能出现在训练集中。**
`dataset_version.filter_sql` 必须包含
`session_id NOT IN (SELECT session_id FROM eval_sample)`，
否则会出现"在训练集上评测"的经典错误——指标虚高但线上无效。

## 检索召回：单路 vs 混合（已跑出数）

```bash
cd apps/python/ai-rag
EMBEDDING_ONNX_DIR=<模型目录> python -m app.eval_cli --sweep 0.05,0.1,0.2,0.5,1.0 --holdout
```

评测集 `retrieval.jsonl`（115 条查询）+ `retrieval-corpus.jsonl`（100 条语料）。
查询手写，**刻意与语料用词不同**——照抄库里的措辞的话 BM25 必赢，三档对比就没有
意义。按难度分三类：`plain` 56 条、`lexical` 42 条（同义不同词，卡 BM25）、
`exact` 17 条（型号/数字/专名，卡向量）。

### 结果（bge-small-zh-v1.5 + Milvus Lite，2026-08-29）

| 检索方式 | R@1 | R@3 | R@5 | R@10 | MRR@10 |
|---|---|---|---|---|---|
| 纯向量 | 0.852 | 0.948 | **0.974** | 0.991 | **0.903** |
| 纯 BM25 | 0.583 | 0.748 | 0.826 | 0.896 | 0.679 |
| RRF 等权融合 | 0.730 | 0.904 | 0.957 | 0.974 | 0.824 |
| RRF 加权（稀疏 0.10） | 0.843 | 0.965 | 0.991 | 1.000 | 0.903 |

**结论：这个评测集上，混合检索没有可主张的收益。**

- **等权 RRF 比纯向量差**（R@5 −0.017，MRR −0.079）。机理：一条只被向量召回、
  排第 3 的文档得分 `1/(60+3)=0.0159`，而两路都平庸（第 20 与第 15）的文档得
  `1/80+1/75=0.0258` —— **"两边都还行"压过了"一边非常对"**。实测样例
  「晚上十一点还有人吗」向量排第 3、BM25 完全召不回（库里写的是 9:00-22:00），
  等权融合把它压到第 13。
- **给稀疏路降权到 0.10 能修好这个压制**，但留出验证（在 57 条上选权重、报另外
  58 条）显示加权融合 R@5 1.000 vs 纯向量 0.983 —— **差 1 条查询，不显著**。

### 这份数字的边界，别越过它说话

1. **评测集偏向向量**：`lexical` 42 条 vs `exact` 17 条是手写时的失衡，
   而 `lexical` 正是 BM25 的死穴。
2. **语料只有 100 条且每条只讲一件事**。BM25 靠稀有词的 IDF 吃饭，
   小语料 + 短文档给不出这个信号；真实知识库里的长文档对它有利得多。
3. **天花板太低**：纯向量 R@5 已经 0.974，只剩 3 条可改进，
   任何方法的提升上限就是 2.6 个百分点。**要让这个对比有信息量，
   得先把评测集做难**（更大语料、更多易混条目）。
4. 换向量化后端数字就会变。这里用的是 91MB 的 bge-small-zh；
   线上默认是 `text-embedding-v4`，跑 `--embedding dashscope` 才是生产数。
