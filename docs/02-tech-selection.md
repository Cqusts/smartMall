# 02 · 技术选型

> 本文记录每个模块的选型结论、理由，以及**被否决的方案与否决原因**。
> 选型的价值一半在"选了什么"，另一半在"为什么没选那个"。

**选型总原则**（按优先级）：
1. 单卡 24G 能跑 —— 跑不动的一票否决
2. 许可证允许商用 —— 电商场景是商业用途
3. 中文效果优先 —— 面向中文电商
4. 可控可调试 —— 作品集要能讲清内部原理，黑盒产品扣分
5. 社区活跃 —— 半年内有实质更新

## 2. 逐项选型说明

### 2.1 Agent 编排：LangGraph

**选中理由**
- 图式状态机，每个节点的状态可持久化、可回放、可从中断处恢复——客服对话需要在"转人工"节点挂起等待，这是 LangGraph 的原生能力
- 原生支持 human-in-the-loop（审核闸门）
- 与 Python AI 生态无缝，能直接调 FunASR、ComfyUI 客户端

**否决项**

| 方案 | 否决原因 |
|---|---|
| **Dify** | 低代码平台，上限在于：自定义的 `knowledge_item` 数据模型塞不进它的知识库抽象；与 Java 侧的审核流、素材关联难以深度集成；作品集里"用 Dify 拖了个流程"讲不出技术深度 |
| **CrewAI** | 角色扮演式协作，适合"多个 Agent 讨论"的场景。本项目的 Agent 之间是**流水线**关系（切片→素材→数据中台→知识库），不是讨论关系，用不上它的核心能力 |
| **AutoGen** | 生态重心在微软栈（Azure OpenAI、Semantic Kernel），本项目用阿里/深度求索的 API，集成收益低 |
| **Coze / 扣子** | 闭源 SaaS，数据出域，且无法自建 |

> 补充：Dify 并非不能用。如果目标改为"最快出可演示效果"，Dify 是更优解。本项目选 LangGraph 是因为定位是**作品集，需要讲清内部机制**。

### 2.2 RAG 引擎：自建

**选中理由**
- 核心数据模型是自定义的 `knowledge_item`（带 `modality`、`asset_ids`、`product_ids`、`valid_from/valid_to`、`review_status`），成品 RAG 引擎的知识库抽象装不下这些字段，尤其是**素材回挂**和**时效性过滤**
- 检索需要按 `product_id` / `category_id` 做元数据过滤 + 时效过滤，这是业务强相关逻辑
- 作品集需要能讲清切分策略、混合检索权重、rerank 的取舍

**否决项**

| 方案 | 否决原因 |
|---|---|
| **RAGFlow** | 强项是 DeepDoc 深度文档解析（复杂版面 PDF/表格），本项目的知识主要来自对话与素材描述，**不是文档**，最大卖点用不上。且是端到端产品，自定义数据模型困难。**部分借用**：如果后期要接入商品说明书 PDF，可单独引入 DeepDoc 做解析器 |
| **FastGPT** | 轻量易用，但知识库模型固定，工作流编排能力与 LangGraph 重叠，引入后架构反而变复杂 |
| **LangChain 全家桶** | 抽象层过厚，调试链路长。只按需引用其 splitter 等工具函数，不用它的 Chain 抽象 |

### 2.3 向量库：Milvus Standalone

**选中理由**
- 2.5 版本内置 **BM25 稀疏检索**，dense + sparse 混合检索一套搞定，**省掉独立部署 Elasticsearch**（省约 2G 内存和一套运维）
- 支持标量字段过滤（`product_id`、`review_status`、`valid_to`），这是本项目检索的刚需
- Standalone 模式单容器可跑，符合单机部署基线

**否决项**

| 方案 | 否决原因 |
|---|---|
| **pgvector** | 更轻量，一套 PostgreSQL 搞定业务+向量+全文，运维成本最低。**否决理由较弱**——若资源紧张可作为降级方案。选 Milvus 是因为混合检索能力更完整，且"向量数据库"在作品集叙事中权重更高 |
| **Elasticsearch + 向量插件** | 向量检索性能弱于专用向量库，且资源占用大（JVM） |
| **Qdrant** | 能力接近 Milvus，但中文社区资料与稀疏检索生态不如 Milvus |
| **Chroma** | 定位是原型/本地开发，不适合作为项目主库 |

### 2.4 数据清洗：Data-Juicer + Label Studio

**Data-Juicer 选中理由**
- 100+ 开箱算子，本项目直接用到的：MinHash 近重复过滤、文本长度过滤、语种识别、乱码/特殊字符过滤、PII 脱敏、敏感词过滤
- 支持自定义算子，业务规则清洗可以写成算子插进同一条流水线
- 配方（recipe）是 YAML，可版本化，符合"数据资产可复现"的要求

**Label Studio 选中理由**
- **ML Backend 机制**是关键：可以把模型清洗的结果作为预标注推给人工，人工只做确认/修正，效率提升数倍
- 支持主动学习——只把模型低置信度的样本推给人工，这直接决定了人工清洗的可行性（不然 100 万条对话人工看不完）
- 同时支持文本、图片、视频标注，覆盖本项目全部标注需求

**否决项**

| 方案 | 否决原因 |
|---|---|
| **Argilla** | 定位偏 LLM 反馈收集与模型调试，与 HuggingFace 生态绑定深。本项目需要的是**通用标注 + 主动学习 + 多模态**，Label Studio 覆盖面更广 |
| **doccano** | 只做文本标注，不支持图片/视频，且无 ML Backend |
| **自己写标注界面** | 纯粹浪费时间，这块没有技术展示价值 |

### 2.5 调度：Airflow 3

**选中理由**：DAG 概念清晰、中文资料多、岗位认知度高；数据清洗流水线本质就是有依赖的批任务。

**否决项**

| 方案 | 否决原因 |
|---|---|
| **Dagster** | software-defined assets 概念其实**更贴合**本项目的"数据资产版本化"。否决理由纯粹是生态与认知度——作品集里 Airflow 更容易被理解。若个人偏好数据资产建模，可替换 |
| **Prefect** | 同上，且国内使用面更窄 |
| **XXL-JOB** | Java 生态调度，但缺少 DAG 依赖编排与数据血缘能力 |

### 2.6 对象存储：SeaweedFS / 阿里云 OSS

> ⚠️ **重要变更**：MinIO 的开源仓库已于 **2026 年 4 月归档**，此前 2 月已归档过一次。现有部署仍可运行，但**不再有新功能、兼容性更新和安全补丁保证**。新项目不应再选用 MinIO。

**选中理由**：SeaweedFS 提供 S3 兼容接口、单机可跑、社区活跃；若愿意付费，直接用阿里云 OSS 更省事（且与 DashScope 同一云，素材传输更快）。

**其他可选**：Garage（轻量、Rust）、RustFS（国内信创方向）、Versity。

**取舍建议**：作品集阶段直接用**阿里云 OSS**——省一个容器的内存，且 CDN 加速对演示视频体验有实际帮助。若要求全本地部署则用 SeaweedFS。

### 2.7 ASR：FunASR

**选中理由**
- Paraformer-large 是中文开源 ASR 的第一梯队，Modelscope 下载量超千万
- **带时间戳预测**——这是直播切片的硬需求，没有精确时间戳就切不准
- 支持热词定制（把商品名、品牌名作为热词，显著提升商品名识别准确率）
- 支持说话人分离（区分主播与助播）
- SenseVoice 作为轻量备选，速度更快

**否决项**

| 方案 | 否决原因 |
|---|---|
| **Whisper / faster-whisper** | 中文效果弱于 Paraformer，中文标点与数字规整化差；时间戳精度不如 Paraformer 的原生时间戳预测 |
| **云 ASR API** | 直播动辄 3 小时，按时长计费成本高；且本地跑 ASR 显存占用小（~2G），没有理由外包 |

### 2.8 直播切片：FunClip 作参考实现 + 自研

**决策**：**借鉴 FunClip，但不直接部署它。**

FunClip 是阿里达摩院开源的自动剪辑工具（v2.1.0，2026-07），基于 FunASR，支持文本关键词切片、说话人切片、LLM 智能切片，带 Gradio 界面。

**为什么不直接用**
- 它是**单机 Gradio 工具**，面向个人用户交互式使用，不是服务；要接进 Kafka 任务流、要与商品库关联、要写素材中心，都得改造
- 本项目的切片逻辑有强业务性：需要按"讲解一个商品"的语义边界切分，并对齐 `product_id`，这是 FunClip 没有的

**借鉴什么**
- 它的 LLM 切片提示词设计
- 时间戳与字幕对齐的处理逻辑
- 其 Gradio 界面可直接作为**人工兜底工具**——自动切片效果不好的场次，运营用 FunClip 手工调整

### 2.9 图像生成：ComfyUI + FLUX / Qwen-Image

**ComfyUI 选中理由**
- 工作流是 JSON，**可版本化、可复现、可参数化**——这是从"能生成图"到"能批量稳定生产"的分水岭
- API 模式（`/prompt` 接口）可被 `ai-media` 服务调用，无需人工点界面
- 生态最全，ControlNet、IP-Adapter、LoRA、各类试穿节点都有现成实现

**模型选择**
- **FLUX.1-dev**：出图质量高。⚠️ 许可证为 **非商用**（FLUX.1-dev Non-Commercial License），仅可用于开发演示；真要商用需用 FLUX.1-schnell（Apache-2.0）或购买商业授权
- **Qwen-Image**：中文文字渲染能力强（电商海报常需要在图上写促销文案），Apache-2.0，**商用推荐**

**关键控制节点**
- **IP-Adapter**：保持商品主体一致性（同一个包，换不同场景背景）
- **ControlNet**：控制构图与姿态
- **CatVTON**：服装虚拟试穿

**虚拟试穿的否决项**

| 方案 | 说明 |
|---|---|
| **CatVTON**（选中） | 约 899M 参数，1024×768 推理显存 <8G，在常规服装替换场景表现均衡，褶皱自然。显存友好是决定性因素 |
| **OOTDiffusion**（否决） | Outfitting Fusion 机制在复杂褶皱和动态姿态上效果最好，但显存与集成成本高，且许可证需确认商用范围 |
| **IDM-VTON**（否决） | ComfyUI 工作流节点繁多，服装样式更换效果不稳定 |
| **Kling / 云端试穿 API**（备选） | 效果稳定、无显存压力，但按次计费且数据出域。作为效果对比的基准线 |

> ⚠️ **合规提醒**：虚拟试穿生成的模特图若使用真人模特照片作为底图，需确认**肖像权授权**范围。建议使用授权素材库或 AI 生成的虚拟模特。

### 2.10 视频生成：Wan2.2-TI2V-5B

**选中理由（决定性的是显存）**
- **Apache-2.0 许可，明确允许商用**
- 采用 3D VAE 高压缩架构（4×16×16），显存占用约 22G，**单张 RTX 4090（24G）可跑 720P@24fps**
- 720P / 5 秒视频生成约 2 分 42 秒 @4090——这个速度使得批量生产成为可能
- 支持文生视频与**图生视频**，图生视频是电商场景的主力（用商品图生成展示视频，主体一致性远好于文生视频）
- 支持光影/构图等电影级参数控制

**否决项**

| 方案 | 否决原因 |
|---|---|
| **HunyuanVideo** | 13B 参数，720p 版本需要 **60G 显存**，推荐 80G 卡。在 24G 基线下**完全不可行**——一票否决 |
| **Wan2.2 的 14B 版本** | 效果更好，但显存需求远超 24G |
| **CogVideoX** | 显存友好但效果与 Wan2.2 有差距，商用许可需逐版本确认 |
| **可灵 / 即梦等云端 API** | 效果最好，无显存压力。**保留为备选通道**：`ai-media` 设计成可切换后端，重要素材可走云端。但作为主力成本不可控 |

### 2.11 TTS：CosyVoice2

**选中理由**
- 中文自然度评测第一，阿里深度优化，支持粤语与方言
- **Apache-2.0，可商用**
- 0.5B 版本支持超低延迟流式合成，显存占用约 2G
- 零样本音色克隆只需 3–10 秒参考音频——可以克隆主播音色做商品口播

**否决项**

| 方案 | 否决原因 |
|---|---|
| **Fish Speech** | 效果不错，但许可证是 **CC BY-NC-SA（禁止商用）**，电商场景直接一票否决 |
| **IndexTTS2** | 零样本控制与情感保真度强（时长精确控制、音色与情感解耦），是**强力竞品**。否决理由是中文自然度 CosyVoice2 更优，且 CosyVoice2 与 FunASR 同属阿里语音栈，模型管理统一。若需要精确控制口播时长（比如卡点视频），可切换到 IndexTTS2 |
| **GPT-SoVITS** | 克隆效果好但需要针对性训练，不适合批量零样本场景 |

### 2.12 微调：LLaMA-Factory

**选中理由**
- 生态最全、中文文档最好、上手成本最低
- 覆盖本项目需要的全部方法：LoRA / QLoRA SFT、DPO
- 支持 Qwen 全系列，含 Qwen3

**否决项**

| 方案 | 说明 |
|---|---|
| **ms-swift** | 在**大规模多模态数据**处理上优于 LLaMA-Factory（数据加载更方便），并深度集成推理/部署/评测，支持更多自定义参数（loss 计算位置、MoE 负载均衡）。MoE 模型训练通过专家并行可提速近 10 倍。**否决理由是本项目微调的是文本风格（7B 稠密模型），用不上它的多模态与 MoE 优势**。若后续要微调 VLM，应切换到 ms-swift |
| **Unsloth** | 单卡训练速度快、省显存，是很好的备选。生态与文档不如 LLaMA-Factory 全面 |
| **裸 PEFT + Transformers** | 灵活但要自己写训练循环、评测、导出，无技术展示增量 |

### 2.13 模型网关：LiteLLM

**选中理由**
- 统一 OpenAI 兼容协议，屏蔽 DashScope / DeepSeek / 本地 vLLM 的接口差异
- **成本核算**：按 token 记账，这是混合模型策略下控制成本的前提
- 失败降级：主模型超时自动 fallback 到备用模型
- 微调模型上线后，只需在网关加一个 model 配置就能做 A/B，业务代码零改动

**否决项**：One API / New API（能力接近，是 Go 实现的 Web 化网关，运维更友好；LiteLLM 胜在 Python 原生可嵌入 `ai-gateway` 服务、且路由策略可编程）。

### 2.14 可观测：Langfuse

**选中理由**
- 不只是监控——**Trace 数据可以直接导出成训练数据**，这与"数据飞轮"的设计完全契合
- 支持在 Trace 上打分（用户点赞/点踩、LLM Judge 评分），评分数据就是 DPO 的偏好信号
- 支持 Prompt 版本管理与 A/B

**这是本项目里少数"监控工具"直接参与核心数据链路的组件**，因此优先级高于普通 APM。

### 2.15 云 LLM：DashScope（通义）/ DeepSeek

**分工**

| 用途 | 模型 | 理由 |
|---|---|---|
| 客服对话主力 | qwen-plus / deepseek-chat | 性价比，中文强 |
| 复杂推理（考核 Judge、语义分段） | qwen-max / deepseek-reasoner | 判断质量优先 |
| 图片理解（VLM） | qwen-vl-max | 电商商品理解能力强 |
| 批量文案生成 | qwen-turbo | 成本优先 |

**为什么不全本地**：Qwen3-VL / Qwen3-Omni 等全模态模型效果很好（Qwen3-Omni 在 36 个音视频基准上拿下 32 项开源 SOTA，延迟 211ms），但在 24G 单卡上与图像/视频生成抢显存，无法共存。混合策略下，**对话走 API、生成走本地**是显存分配的最优解。

**为什么不全 API**：图像、视频、ASR、TTS 走 API 的成本随生产量线性上涨，而这几项恰恰是本项目要批量跑的；且微调必须本地。

## 3. 显存预算校验

选型必须通过这张表的检验（单卡 24G）：

| 组件 | 显存 | 驻留方式 |
|---|---|---|
| FunASR Paraformer-large | ~2G | 常驻 |
| CosyVoice2-0.5B | ~2G | 常驻 |
| bge-m3 + bge-reranker | ~2G | 常驻 |
| **常驻小计** | **~6G** | |
| ComfyUI + FLUX fp8 | ~16G | 独占轮转 |
| Wan2.2-TI2V-5B | ~22G | 独占轮转（需卸载常驻模型） |
| CatVTON | ~8G | 独占轮转 |
| QLoRA 微调 Qwen3-8B | ~20G | 独占轮转（需卸载常驻模型） |
| vLLM 部署 Qwen3-8B (AWQ) | ~10G | 独占轮转 |

**结论**：Wan2.2 和 QLoRA 训练需要**清空常驻模型**才能跑。因此：
- 视频生成与训练任务安排在业务低峰（夜间）
- Kafka 对应 topic 单分区单消费者，强制串行
- 需要显存看门狗做常驻模型的卸载/重载

若升级到 **48G 卡（L20 / A6000）**，上述约束全部解除，可全部常驻。详见 [14 · 基础设施](14-infra.md)。
